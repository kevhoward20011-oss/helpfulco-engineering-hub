AI-Assisted Software Repair Lab

The question was simple: can modern AI coding tools do more than generate demo code? We tested them on broken states from mature software projects, required a reproducible failure first, kept the reference repair hidden, then verified the proposed fix with real tests and runtime evidence.

● Four repair cases completed or verified against the reproduced failure

Why we did it

Test the engineering process, not the sales claim.

Instead of saying “AI can code”, we wanted evidence that AI tools can help investigate unfamiliar code, work through real failures and produce repairs that survive verification.

The method

  • Start from a real issue or benchmark: use a known broken state from an established project.
  • Reproduce the defect first: no repair attempt counts until the failure is visible locally.
  • Protect the broken baseline: pin the commit and record the failure evidence.
  • Keep the reference answer hidden: the AI solver works from the repository and failure evidence, not the upstream patch.
  • Verify the repair: rerun the focused test or production reproduction and check wider regressions where practical.
  • Review AI output: a passing first attempt is not automatically trusted; gaps are challenged and corrected.

Tools used

Tests/runtimethe final authority: Maven, Python test suites, TypeScript checks and production-style runtime reproduction
The important part: AI was not treated as the evidence. The failing program and the passing verification were the evidence.
Repair evidence

Four different kinds of software failure.

The cases deliberately span languages, frameworks and failure modes so the evidence is about problem-solving capability rather than familiarity with one stack.

01

Google Gson — historical Java test repair

Problem: a historical allocator-instantiation test used an assertion pattern that modern Error Prone identified as ignored assertion failure behaviour.

What we did: reconstructed the historical Java environment, confirmed the baseline behaviour, then gave the broken test state to the AI solver without the upstream answer.

What the AI changed: replaced the try/fail/catch pattern with assertThrows and corrected the adjacent interface case.

Result: target test passed and the repair pattern matched the later upstream implementation. Limitation: on this machine the defect surfaced as an Error Prone warning rather than the benchmark's fatal compile failure.
02

Sonar CXX — executable-line expectation mismatch

Problem: the test expected 23 executable lines but the implementation produced 55, causing a real failing test in a historical Maven/Java codebase.

What we did: recovered the old Java/Mockito runtime requirements, reproduced the exact 23-versus-55 failure, then handed the red state to the AI solver.

What the AI changed: updated the expected executable-line count and list to the actual 55-line behaviour.

Result: the target test passed and the repair matched upstream except for formatting. This case also showed why environment archaeology matters: an old Mockito/CGLIB stack needed Java module access before the real defect could even be seen.
03

SymPy — subclass behaviour lost across operations

Problem: a subclass of Permutation was created correctly, but inversion, exponentiation and multiplication returned the base Permutation type instead of preserving the subclass.

What we did: recreated the old Python environment, wrote a clean behavioural reproduction and let the AI solver repair the production implementation.

What happened next: the first AI pass was useful but incomplete. Independent review found three gaps in construction semantics, exponentiation type handling and rmul_with_af. The AI was sent those gaps — not the upstream code — and corrected them.

Result: the required subclass behaviour was restored and focused/wider tests passed apart from known pre-existing failures. This is the strongest example of why AI output still needs engineering review rather than automatic acceptance.
04

Next.js — production request-body race

Problem: a production standalone Next.js path could let middleware/proxy code read a request body while a downstream Server Action later received incomplete JSON. The reproduced failure was SyntaxError: Unexpected end of JSON input.

What we did: fixed only the local standalone packaging needed to run the supplied reproduction, then captured the real red-state evidence: the proxy read 50,333 bytes and the downstream action crashed.

What the AI diagnosed: a missing ordering guarantee around request-body replacement. The deliberately widened race was then used to stress the repair rather than relying on a lucky green run.

Result: patched reproduction 5/5 successful requests; final build 15/15 successful requests; one 7.2 MB slow-streamed request returned 200; ESLint and tsc --noEmit were clean; no JSON parse error appeared in the server log. Limitation: the stock race is timing-sensitive and can pass when the window is very small; upstream repair comparison is deliberately kept separate until after solver evidence is frozen.
What this proves

Useful AI engineering is more than generating code.

These cases show a repeatable way to turn AI coding tools into a supervised software-repair capability.

Unfamiliar codebaseswork can begin from the failure and repository evidence rather than prior ownership of the code
Environment recoveryold Java/Python/runtime constraints are separated from the actual software defect
Production debuggingruntime races and cross-layer failures can be investigated, not just unit-test assertions
Human verificationAI repairs are reviewed, challenged and tested before being treated as complete

The commercial translation

A customer does not need to buy “AI coding”. They need a broken software problem solved. The practical service is: give us the repository, the failure and the constraints; we reproduce it, isolate the cause, use AI tools to accelerate the repair, then return a tested patch and an evidence trail.

Typical fit: existing SaaS bugs, API failures, database/query behaviour, framework regressions, failing tests, release-only failures, integration problems and inherited code nobody on the current team fully understands.

What we are not claiming

  • AI can solve every software problem.
  • A green first attempt should be trusted without review.
  • Benchmarks are the same as maintaining a customer's production system.
  • One successful repair proves expertise in every language or framework.

The evidence supports a narrower and more useful claim: with access to the code, a reproducible failure and disciplined verification, AI tools can materially extend the range and speed of software problems one engineer can investigate and repair.

Evidence discipline

Reference answers come last.

The upstream or benchmark repair is used as an independent comparison only after the solver has finished. That keeps the case useful as evidence of diagnosis rather than answer copying.

Red state first

Record the broken commit, local environment and exact failure before changing production code.

Solver separation

Do not expose the gold patch or later upstream implementation to the coding agent during diagnosis.

Evidence after repair

Keep the diff, test output, limitations and any gap between local reproduction and the original report visible.
