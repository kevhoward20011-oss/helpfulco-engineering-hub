Broken software in. Tested repair out.

The customer problem is not “I need AI coding”. It is “something important is broken and I need it working again.” These cases show the process: reproduce the failure, isolate the cause, use modern engineering and AI tools where they help, then verify the repair before calling it done.

Why we did it

Prove the repair process, not the tool.

Anyone can open an AI coding tool. The useful question is whether a broken system can be understood, repaired and verified without blindly trusting the first answer.

The repair method

  • Start from a real failure: use a known broken state from an established project.
  • Reproduce it first: no repair attempt counts until the failure is visible locally.
  • Protect the baseline: pin the commit and record the failure evidence.
  • Keep the reference answer hidden: the coding agent works from the repository and failure evidence, not the upstream patch.
  • Repair the smallest relevant surface: avoid unrelated refactors and dependency changes just to make the symptom disappear.
  • Verify before accepting: rerun the focused failure, wider checks where practical, and record limitations honestly.

Where AI fits

ChatGPTproblem framing, environment reconstruction, review and evidence discipline
OpenCoderepository-level coding workflow and controlled repair environment
Space Bunnyindependent diagnosis and implementation inside the broken repository
Tests/runtimethe final authority: the software must demonstrate that the repair works
The important part: AI is part of the toolkit, not the product and not the evidence. The deliverable is the repaired software, the test result and a clear record of what changed.
Upstream return rule: after the independent repair is frozen, check the originating project. If the defect is still open and the repair is not already present, prepare a focused upstream issue or pull request with the reproduction and verification evidence. If upstream has already fixed it, link the original issue and merged fix instead of claiming duplicate work.
Repair evidence

Four different kinds of software failure.

The cases span languages, frameworks and failure modes. The point is not that one tool “knows everything”; it is that the same disciplined repair process can be applied to unfamiliar systems.

01

Google Gson — historical Java test repair

Problem: a historical allocator-instantiation test used an assertion pattern that modern Error Prone identified as ignored assertion failure behaviour.

What we did: reconstructed the historical Java environment, confirmed the baseline behaviour, then gave the broken test state to the AI solver without the upstream answer.

Repair: replaced the try/fail/catch pattern with assertThrows and corrected the adjacent interface case.

Result: target test passed and the repair pattern matched the later upstream implementation. Limitation: on this machine the defect surfaced as an Error Prone warning rather than the benchmark's fatal compile failure.
02

Sonar CXX — executable-line expectation mismatch

Problem: the test expected 23 executable lines but the implementation produced 55, causing a real failing test in a historical Maven/Java codebase.

What we did: recovered the old Java/Mockito runtime requirements, reproduced the exact 23-versus-55 failure, then handed the red state to the AI solver.

Repair: updated the expected executable-line count and list to the actual 55-line behaviour.

Result: the target test passed and the repair matched upstream except for formatting. The case also showed why environment recovery matters: an old Mockito/CGLIB stack had to run correctly before the real defect could even be seen.
03

SymPy — subclass behaviour lost across operations

Problem: a subclass of Permutation was created correctly, but inversion, exponentiation and multiplication returned the base Permutation type instead of preserving the subclass.

What we did: recreated the old Python environment, wrote a clean behavioural reproduction and let the AI solver repair the production implementation.

Review mattered: the first AI pass was useful but incomplete. Independent review found three gaps in construction semantics, exponentiation type handling and rmul_with_af. The solver was given those gaps — not the upstream code — and corrected them.

Result: the required subclass behaviour was restored and focused/wider tests passed apart from known pre-existing failures. This case demonstrates why the engineering value is not “press a button and trust AI”; it is diagnosis, review, correction and verification.
04

Next.js #85416 — production request-body race

Original report: vercel/next.js issue #85416 described a timing-dependent race in Node.js middleware body cloning where a downstream Server Action could receive incomplete JSON.

Problem reproduced: the proxy read 50,333 bytes while the downstream action failed with SyntaxError: Unexpected end of JSON input.

What we did: fixed only the local standalone packaging needed to run the supplied reproduction, independently diagnosed the missing ordering guarantee around request-body finalisation/replacement, and deliberately widened the race window so the repair could be stress-tested instead of relying on one lucky green run.

Independent verification result: patched reproduction 5/5 successful requests; final build 15/15 successful requests; one 7.2 MB slow-streamed request returned 200; ESLint and tsc --noEmit were clean; no JSON parse error appeared in the server log. Important limitation: the stock race is timing-sensitive and can pass when the window is very small.

Upstream status: this was not a new HelpfulCo upstream fix. Next.js had already merged the corresponding fix in PR #85418 on 14 November 2025, adding the required await before continuing. Our case is evidence that we independently reproduced the defect, arrived at the same ordering fix and verified it under stressed timing and slow-streamed input.

Software rescue

You are not paying for access to AI. You are paying to get the software working again.

Owning ChatGPT or another coding tool is not the same as taking responsibility for a broken system, finding the real cause and proving the repair.

What you hand over

  • The repository or codebase.
  • The failure, error, broken behaviour or failing test.
  • The environment and constraints that matter.
  • Anything that must not be changed or broken.

What comes back

  • A reproduced and understood failure.
  • A focused repair rather than an unexplained rewrite.
  • Tests or runtime evidence showing what now works.
  • A record of what changed, what was checked and what remains uncertain.
Unfamiliar codebasesstart from the failure and repository evidence rather than needing years of ownership
Environment recoveryseparate old runtime or dependency problems from the defect the customer actually cares about
Production debuggingtrace runtime races and cross-layer failures, not just obvious syntax errors
Verified deliverythe repair is accepted because tests and runtime evidence support it, not because an AI said it looked right

Typical fit

Existing SaaS bugs, API failures, database/query behaviour, framework regressions, failing tests, release-only failures, integration problems and inherited code nobody on the current team fully understands.

The value is time and ownership: instead of spending a day or a week experimenting with prompts and patches, the problem is worked through as an engineering job with a defined outcome and evidence.

What we are not claiming

  • AI can solve every software problem.
  • A green first attempt should be trusted without review.
  • Benchmarks are the same as maintaining a customer's production system.
  • One successful repair proves expertise in every language or framework.

The evidence supports a narrower and more useful claim: with access to the code, a reproducible failure and disciplined verification, modern AI tools can extend the range and speed of software problems that can be investigated — while responsibility for the final repair stays with the engineer.

Evidence discipline

Reference answers come last.

The upstream or benchmark repair is used as an independent comparison only after the solver has finished. That keeps the case useful as evidence of diagnosis rather than answer copying.

Red state first

Record the broken commit, local environment and exact failure before changing production code.

Solver separation

Do not expose the gold patch or later upstream implementation to the coding agent during diagnosis.

Evidence after repair

Keep the diff, test output, limitations and any gap between local reproduction and the original report visible.
