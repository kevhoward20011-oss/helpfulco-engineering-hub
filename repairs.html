Stripe Terminal React Native #1140 — intent-cache concurrency

Status: VERIFIED FIX ACCEPTED / MERGED.

Broken: the Android React Native bridge used ordinary mutable intent caches across code paths that can run concurrently.

Result: we reproduced the concurrency defect, implemented the narrow cache-synchronisation repair and added focused regression coverage.

Verification: focused concurrency test 5/5 and stable across 10 runs; Android unit suite 233/233; JavaScript 238/238; iOS 166/166; clean diff check. Verification was JVM/unit-test level rather than a physical-device reproduction.

Upstream outcome: Stripe collaborator review: APPROVED — “LGTM”. The PR was merged on 2 October 2026.

Public provenance: stripe/stripe-terminal-react-native PR #1140. Authored by kevhoward20011-oss / HelpfulCo Innovations Ltd.

B

Google go-jsonnet #484 — post-fork deadlock

Status: VERIFIED SOLUTION POSTED / UPSTREAM ADOPTION PENDING.

Broken: after the Go runtime was initialised in a parent process, a Linux fork() child could enter inherited runtime state whose supporting threads no longer existed and hang indefinitely.

Result: the repaired path detects the unsafe post-fork condition before entering jsonnet_make() and fails immediately with an actionable error rather than hanging.

Verification: unpatched Linux case hung for 300+ seconds; repaired path fails immediately. Regression matrix 4/4; Python 14/14 on Linux and macOS; C-bindings compatibility 31/31; normal evaluation and spawn paths passed.

Public provenance: HelpfulCo’s public technical submission on google/go-jsonnet #484. The upstream issue remains open, so this is not presented as an accepted Google patch.

Vercel Eve #4024 — approved batch remains parked

Status: INDEPENDENT VERIFICATION POSTED — NOT OUR FIX.

Broken: when two pending approval batches were approved together, one approved call could remain parked until another event woke the session.

Our contribution: reproduced the stuck second batch on Windows, tightened the fixture to match production turn behaviour and checked the acceptance condition against Vercel’s #4027 fix direction.

Evidence: the public submission links our evidence branch and commit so the reproduction and acceptance contract are independently inspectable.

Public provenance: HelpfulCo independent verification on vercel/eve #4024. We do not claim authorship of Vercel’s fix.

How we label the work

  • Reproduced — the failure has been demonstrated.
  • Root cause identified — the causal path is understood.
  • Patch prepared — a candidate repair exists.
  • Locally verified — the repaired path has passed our verification.
  • Upstream verification required — the final environment is outside our control.
  • Upstream verified / accepted — the external project has confirmed or adopted the result.

Why the distinction matters

Some defects require specialist hardware, closed components, production infrastructure or the original reporter’s environment. In those cases the correct engineering result may be a verified local solution plus a clearly defined upstream verification step.

We do not turn “looks right” into “fixed”.

Next.js #85416 — request-body race

Status: verified independent repair of a historical upstream bug.

Broken: a timing-dependent request-body race could leave a downstream Server Action with incomplete JSON.

Impact: production-style requests could fail even though the same path sometimes appeared healthy.

Public provenance: vercel/next.js issue #85416. The upstream issue had already been fixed by Next.js in PR #85418. This portfolio case claims independent reproduction, repair and verification only — not authorship of the upstream fix.

04

go-jsonnet #484 — Python binding post-fork deadlock

Status: verified independent repair of the reproduced deadlock behaviour; upstream issue remains open and this is not presented as an accepted upstream patch.

Broken: after the Go runtime was initialised in a parent process, a Linux fork() child could enter jsonnet_make() with inherited runtime state whose supporting threads no longer existed. The result was a deterministic 0%-CPU hang.

Repair: detect the unsafe post-fork process state before entering jsonnet_make(), then fail immediately with an actionable error instead of entering a Go runtime state that cannot safely recover.

Our verification: the unpatched Linux case hung for 300+ seconds; the repaired path fails immediately. Regression matrix 4/4; full Python suite 14/14 on Linux and macOS; C-bindings compatibility 31/31; go test ./... reported no failures; normal evaluate_snippet, evaluate_file, spawn and parent-process operation all passed. No public ABI change.

Environment lesson: macOS alone produced a false pass because the inherited Go runtime state differed. Linux verification exposed the earlier jsonnet_make() deadlock, so the final defence was moved ahead of that call.

Public provenance: google/go-jsonnet issue #484. HelpfulCo's claim is limited to independent reproduction, repair and verification of the observed deadlock behaviour in the tested environments.

05

Stripe Terminal React Native #1140 — concurrent intent caches

Status: verified HelpfulCo fix, reviewed by Stripe and merged upstream.

Broken: in-memory PaymentIntent and SetupIntent caches in the Android React Native bridge were backed by ordinary mutable maps while bridge calls and Stripe SDK callbacks can access lifecycle state concurrently.

Repair: use synchronised map wrappers and preserve the surrounding behaviour, with focused regression coverage for concurrent access.

Our verification: focused test 5/5 passing and stable across 10 consecutive runs; Android 233/233; JavaScript 238/238; iOS 166/166; clean diff check. Stripe collaborator review approved the PR with “LGTM”, and it was merged.

Scope: this claim is limited to the reproduced Android React Native bridge cache-concurrency defect. It does not claim to fix the separate native Android #747 issue, and no analogous iOS defect was reproduced.

Public provenance: stripe/stripe-terminal-react-native PR #1140.

Software rescue

Your engineers know the system. Bring us the problem that is consuming their time.

Fix Factory is designed as an escalation route for stubborn defects: difficult, intermittent, cross-stack or simply too expensive to keep circling internally.

Good problems to send

  • A bug that keeps coming back.
  • An app or AI-built project that is nearly working but stuck.
  • An API, database or integration failure.
  • A release-only or environment-specific failure.
  • Inherited code nobody wants to touch.
  • A difficult public issue your team has not had time to solve.

What you get

  • A focused investigation of the actual failure.
  • A repair or bounded solution where the evidence supports one.
  • Verification showing what now works.
  • A clearly stated next verification step where the final environment is outside our control.

No inflated claims. No mystery “AI says it works” hand-off.
