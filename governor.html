Sovereign AI Governor

A governance layer designed to stop an AI recommendation becoming a consequential action unless evidence, authority, policy and - where required - human approval are present. The strongest engineering story is not the UI; it is the controlled decision and execution path.

Three engineering problems

What this project is worth discussing in an interview.

Each problem is framed around a technical constraint, the architecture used to handle it, what worked in the implementation, and what is currently evidenced.

01

How do you stop an AI proposal bypassing human authority?

Separate decisioning from execution. The Decision Centre is non-executing; approval state and authority are carried into a bridge; the HardToolGateway remains the execution-authorisation boundary.

What worked: The implementation keeps a decision or recommendation from becoming execution merely because the AI proposed it; the path into execution remains a separate, inspectable authorisation boundary.
● Static implementation evidence
02

How do you fail closed when evidence or approval is missing?

The core lifecycle represents allowed, approval-required, blocked, malformed and unknown states. Execution security includes restricted/emergency safe states and approval consumption/replay controls rather than assuming success.

What worked: Missing, malformed or unapproved states have explicit non-executing outcomes, so the system has a defined safe path instead of relying on optimistic fall-through.
● Static implementation evidence
03

How do you prove what happened after the decision?

Authenticated evidence, authoritative SQLite state, MAC/hash-linked audit records, checkpoints and append-only ledger primitives create an evidence trail that can be inspected and reconstructed.

What worked: Decision, authority and execution evidence are represented as retained records with integrity and checkpoint mechanisms, giving later inspection something concrete to reconstruct instead of relying on logs of convenience.
● Static implementation evidence

Credibility matters

Known limitations stay visible.

A good engineering portfolio should show the edge of the evidence, not smooth it away.

Fresh full-suite status not established by this audit

The audit was read-only and did not execute the current test suite. No current pass total is claimed here.

Static concerns still require targeted verification

The audit flagged areas including payload-digest propagation, caller-controlled authority/time and execution-expiry handling for follow-up before any stronger public assurance claim.

Live action remains outside this demo story

The employer demo should stay local/simulated and demonstrate the governance boundary rather than enabling live apply or live trading.

Private implementation stays private

The Hub exposes architecture and selected evidence references, not the full private codebase.
