Sovereign AI Governor

A provider-neutral governance layer designed to keep AI proposals separate from execution authority. The engineering focus is explicit authority, evidence, human approval where required, hard execution boundaries, single-use permits, recovery and forensic evidence.

Architecture

Authority before action.

The design treats the AI as a proposer, not the authority. Permission to act is carried through a controlled path and bound to the exact governed action.

Constitution Engine→Authority & Evidence Decision→Human Authority where required→Hard Execution Boundary→Evidence & Recovery→Change Certification

Execution controls

  • Provider & Action Normalisation: external actions are translated into a governed form before authority is evaluated.
  • Current Operating Envelope: runtime authority is tied to the active operating constraints rather than an informal prompt.
  • Single-use permits: execution authority is bound to the intended action and relevant Constitution/policy/Operating Envelope state.
  • Hard Tool Gateway: the controlled execution path remains the authority boundary; browser or UI approval alone is not execution authority.

Agent identity

  • Agent Passport: enforceable identity/scope is checked at action admission.
  • Lifecycle persistence: passport state is persisted and restored with fail-closed integrity checks.
  • Revocation: lifecycle authority can revoke a passport without granting execution authority.
  • Gate 9 scope: the governed GitHub read requires github:repository:read; older active passport state must be re-provisioned or recreated to carry that scope.

Durable review context

The Decision Centre restart path was hardened so a consequential action waiting for human review can retain the context needed to validate the later decision rather than relying on ephemeral process state.

Why it matters: an approval after restart must still refer to the same governed action, authority and review context. A stale or unverifiable review context must fail closed.

Current limitations

What TRL 6 does not mean.

These constraints are part of the evidence, not footnotes to hide.

External dependency remains bounded but real

The GitHub demonstration currently depends on unauthenticated API/network availability and its approximate unauthenticated rate limit. No credential is used for that Gate 9 path.

Schema handling fails closed

GitHub schema drift is constrained through a strict whitelist. Independent re-verification focuses on stable fields including repository ID, full name and the recorded commit rather than treating volatile metadata as a stable trust anchor.

Gate 9 did not exercise every subsystem

The Constitution Engine was not exercised in the Gate 9 GREEN path. Gate 9 proves the scoped external-action path; it does not by itself re-prove every Governor component.

Verifier independence has limits

The verifier is a separately-run process using trusted local key custody. It is not third-party verification, externally anchored verification or independent-key-custody verification.

Cross-platform evidence is specific

Local Windows storage adapters still require a Windows execution host. Gate 9 addressed the external-network gap through Linux OCI and should not be presented as proof that Windows-specific adapters run in Linux.

Passport migration is explicit

Existing states carrying an active Agent Passport from before Gate 9 need re-provisioning or a fresh state to receive the new github:repository:read scope.

Production readiness

Production hardening is the next category of work — not evidence that Gate 9 failed.

TRL and production readiness answer different questions. The prototype evidence can justify TRL 6 while the following operational controls remain unfinished.

Identity and key operations

  • Key and credential rotation.
  • Login throttling and lockout.
  • Multi-factor authentication.
  • Operational Agent Passport lifecycle tooling.

Infrastructure and external assurance

  • Secret-manager integration and in-path TLS.
  • External evidence/audit anchor.
  • Production observability and alerting.
  • Independent re-audit and stronger independent key custody.
Claims deliberately not made: production-ready, independently certified, third-party verified, externally anchored, or proven safe for unrestricted autonomous execution.
